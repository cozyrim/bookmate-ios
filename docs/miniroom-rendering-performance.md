# 미니룸 탭 전환·스크롤 끊김 개선

## 문제와 판단

미니룸 진입·복귀와 책장 좌우 스크롤에서 끊김 발생. 배경·책장·책 제목·프로필이 함께 표시되는 화면이라 네트워크 요청과 화면 계산 비용을 나누어 확인할 필요.

실제 iPhone에 Instruments를 Attach하고 Time Profiler·Allocations·Animation Hitches·Network로 관찰. 미니룸의 상태 구독과 View 구조를 우선 개선 대상으로 선정.

## 해결 과정

아래는 개선 당시 `perf-miniroom-before`와 `perf-miniroom-after` 사이의 변경. 비공개 개발 저장소의 태그 차이와 개인 개발 기록을 대조.

| 변경 | 선택 이유 |
| --- | --- |
| `MiniRoomBooksStore`에서 책 데이터만 구독 | 전체 ViewModel의 다른 상태 변화가 미니룸까지 영향을 주는 범위 축소 |
| 직접 드래그 계산을 `ScrollView + LazyHStack + paging`으로 변경 | 기본 스크롤 동작을 활용하고 페이지 View를 지연 생성 |
| 한 페이지면 `bookPage`만 표시 | 불필요한 스크롤 구조 제거 |
| 글자별 `Text`를 여러 줄 `Text` 하나로 변경 | 제목을 구성하는 View 수 축소 |
| 배경 PNG 약 3.03MB → JPG 약 0.57MB | 배경 에셋 파일 경량화 |

## 결과 및 배운 점

| 지표 | 개선 전 | 개선 후 | 감소율 |
| --- | ---: | ---: | ---: |
| Animation Hitches 총 지속 시간 | 4,420ms | 483.93ms | **89.1%** |
| Hitch 수 | 68회 | 25회 | **63.2%** |
| Allocations Persistent | 57.97MiB | 33.43MiB | **42.3%** |

감소율은 `(개선 전 − 개선 후) ÷ 개선 전 × 100`으로 계산해 소수 첫째 자리 반올림. 이 값은 앱 전체의 성능 향상률이나 메모리 사용량 감소율이 아닌 해당 측정 구간의 지표.

- 화면 분리만으로 끝내지 않고, 어떤 상태를 관찰하는지까지 함께 확인할 필요.
- 화면 계산 비용은 Time Profiler, 끊김은 Animation Hitches로 비교해 원인 후보와 사용자가 겪는 현상을 연결.
- 여러 변경을 함께 적용했으므로 특정 변경 하나가 개선율 전체를 만들었다고 단정하지 않음. 이미지 파일 용량 감소율과 메모리 감소율도 구분.

## 측정 조건과 해석 범위

- 도구: 실제 iPhone에 Attach한 Instruments. 기기 모델·OS·빌드 설정·책 수·전체 기록 길이는 원문에 미기재.
- 공통 시나리오: 앱 실행 → 홈 → 미니룸 → 좌우 스크롤 4회(좌2·우2) → 책 상세 → 뒤로가기 → 홈 → 미니룸 재진입.
- 전후 한 쌍의 집계값. 원문의 ‘3회 이상 반복 측정’은 후속 계획이므로 이 수치를 반복 측정 평균으로 소개하지 않음.
- 근거: 개인 노션 「미니룸 성능 개선 포트폴리오 정리」와 옵시디언 「북메이트 - 미니룸 렌더링 성능 개선」을 2026-09-22 대조. 원시 trace 재분석이나 최신 앱 재측정은 수행하지 않음.

## 현재 코드와의 차이

현재 [MiniRoomBookshelfView](../BookMate/Social/MiniRoom/MiniRoomBookshelfView.swift)는 `LazyHStack` 페이징과 단일 페이지 분기를 유지. [RoomTabView](../BookMate/Main/RoomTabView.swift)의 `MiniRoomBooksStore`도 책 데이터만 구독하는 구조를 유지. 다만 책 제목은 후속 변경으로 다시 글자별 `Text`를 사용하는 구조.

따라서 위 수치는 **개선 당시 버전의 결과**로 한정. 최신 버전의 성능은 같은 시나리오로 다시 측정해야 하며, 과거 수치를 현재 버전의 성능 보장으로 사용하지 않음.
